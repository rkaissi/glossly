# Architecture

How Glossly is put together: the processes, the packages, and where each concern lives. For what each feature does, see `docs/features.md`. For why things are the way they are, see `docs/decisions.md`.

## Processes

```
 C# helper (helpers/windows)          Electron main (packages/shell-electron/src/main)
 glossly-helper.exe                    tray, hotkeys, capture session, IPC, services
   mouse hook, UIA reads,   <-- JSON lines over stdin/stdout -->   HelperClient (core)
   clipboard, focus, popups                       |
                                                  +-- utilityProcess: embed-worker (transformers.js)
                                                  +-- overlay window   (packages/ui overlay.html)
                                                  +-- settings window  (packages/ui settings.html)
```

- **Helper** (`helpers/windows/`, .NET 10, FlaUI.UIA3 plus raw `IUIAutomation` interop). A JSON-lines loop: one request at a time on the MTA main thread, a queued stdout writer thread so the hook callback never blocks, a `ready` event on start, exit on stdin EOF. The mouse hook and the mouse-down baseline snapshot (`Baseline.cs`) run on their own threads. `helpers/protocol.md` documents every command, error code, and event; read it before touching helper code. Commands: `selection`, `context`, `context_container`, `context_caret`, `copy_fallback`, `paste`, `foreground`, `restore_focus`, `focus_field`, `popups_near`, `baseline`, `window_corners`, `mouse_hook`, `input_watch`. Password fields are always refused.
- **Main** owns the selection. Renderers refer to it by `sessionId` and never send text back, except `clipboard:write` for Ctrl+C in a panel.
- **Embed worker**: a `utilityProcess` running `@glossly/core/embed`. Starts at launch if the model is downloaded (meta `embed_downloaded`) or setup is finished, otherwise on `embed:download`, then backfills `itemsWithoutVectors`, then syncs the vectors of people, tasks, and events (`EmbedHost.syncContext`, decision 77).
- **Overlay**: one transparent, frameless, `focusable:false`, always-on-top (`pop-up-menu`) window, created once and shown with `showInactive`. It takes focus only on the hotkey path or for panels that need typing.
- **Settings window**: a normal framed window with mica, title "Glossly". The only window with a taskbar button.

## Packages

pnpm monorepo. `@glossly/core` ships TypeScript and is bundled into main by electron-vite. Imports are extensionless (bundler resolution). Prompts are loaded with `?raw` (`core/src/env.d.ts`).

### `packages/shell-electron` (Electron main and preload)

- `index.ts`: single-instance lock (a second launch calls `app.exit(0)` and the running one opens Settings), wiring, tray, hotkeys, first run (opens `#setup` while `firstRunComplete` is false), `setAppUserModelId('com.glossly.app')`.
- `services.ts`: Store, settings cache and `setSetting` (Zod per key), `AiSdkLlm`, `SaveService`, `Metrics`, `PeopleRepo`, keys, catalog refresh (24 h), role updates, delete-all and reset.
- `capture.ts`: the capture session. Auto and hotkey paths, expand, routing merge, tier-2 reads, every action's main-side half, insert and paste, save modes, the close logic and its reasons, and the Who/Visualize/Reply caches. The largest file; most behavior bugs land here.
- `overlay.ts` (window, `SIZES`, `MAX_W` 680, material and DWM corners, `resize()`), `view.ts` (pure helpers: slot labels, `growFrom`, `fitOnScreen`, `Lru`, `ExpiringLru`, `replyCacheKey`; unit tested), `helper-manager.ts` (spawn, restart with 0.5 to 10 s backoff, re-send `mouse_hook` and corners on `ready`), `hotkey.ts` (main hotkey and `SaveHotkey`), `ipc.ts` (every invoke handler; accepts only the overlay or settings webContents), `keys.ts` (`safeStorage` files, decrypted keys in memory only), `reminders.ts`, `tray.ts` (icon drawn in code), `settings-window.ts` (also the Try it capture source; `Capture` pushes `setup:tried` to it when a pill, bar, or action comes from that window), `embed-host.ts`/`embed-worker.ts`, `paths.ts`, `log.ts` (codes and timings only), `smoke.ts`.
- `electron.vite.config.ts`: main has two entries (`index`, `embed-worker`); `sqlite-vec` and `@huggingface/transformers` stay external. The preload is CJS (`out/preload/index.cjs`) so windows can be sandboxed. The renderer root is `../ui` with two pages. A build-only plugin injects a strict CSP (`script-src 'self'`; the dev server needs an inline refresh script).

### Packaging (Step 22, decision 69)

Releases are built by `.github/workflows/release.yml` on a pushed `v*` tag (decision 73; `scripts/release.mjs tag`, `status`, `download`, `publish`), into a draft release that `publish` turns into the release; the steps below are what it runs, and they still work locally. `pnpm dist` (repo root) runs `helper:publish` (self-contained win-x64 into `helpers/windows/publish`), then `electron-vite build` and `electron-builder --win --publish never` in `packages/shell-electron` with `electron-builder.config.cjs` (JavaScript so it can read the GitHub owner and repo for the update feed from `git remote get-url origin`). Output in `packages/shell-electron/dist/` (git-ignored): `Glossly-Setup-<version>.exe`, its `.blockmap`, and `latest.yml`; the packaged app carries `resources/app-update.yml`. `@glossly/core` is a dev dependency because it is bundled into main; only `sqlite-vec` and `@huggingface/transformers` ship as `node_modules`, with their native parts in `app.asar.unpacked`. Packaged paths: the helper in `resources/helper`, `icon.png` and `icon.ico` in `resources` (`paths.ts`). `electronVersion` in the config must match the installed electron (electron-builder rejects the `^` range). `extraMetadata.name: glossly` names the install folder; the app's name and data folder come from `productName`. **Updates** (decision 70): `src/main/updater.ts` (`Updater`) wraps electron-updater, pushes `updates:state` to the settings window, answers `updates:get`, `updates:check`, `updates:download`, `updates:install`, and runs the installer from the end of `before-quit` (`finish`); `updateErrorKind` in `core/src/updates/errors.ts` sorts failures (404 and no release mean none).

## The capture pipeline

1. **Auto path.** Helper `mouse_up` (drag or double-click, outside the overlay and Glossly's pids) → `foreground` → `gateApp` (block list, per-app modes, hotkey-only apps) → `selection` → `gateAutoSelection` → `baseline` (the helper's own mouse-down snapshot) → `pollForToolbar` with `popups_near` → `placePill` → show inactive. A generation counter drops stale captures.
2. **Hotkey path.** `foreground` → `selection` → `copy_fallback` if `mayCopyFallback` → `context` (tier 1) → bar shown focused. Nothing selected: `context_caret` reads the surroundings (text around the caret, or visible text) before the bar takes focus.
3. **Expand.** Tier 1 → `Router.quick` paints Ask and Save → `Router.route` fills slots 3 and 4 (`mergeRoute`). Recall and person badges are computed alongside, locally.
4. **Action click.** Records `action_clicked {action, ms}`, reads tier 2 once (`context_container`, with the focus hand-off on the hotkey path), opens the panel.
5. **Insert.** `insertText`: `restore_focus` on the source, check the focused element is editable (Reply can `focus_field` to find the reply box), close, `paste`. Any failure puts the text on the clipboard with a note.

Context tiers: **tier 1** is `capture.contextChars` (500) around the selection, read on expand. **Tier 2** is up to `capture.containerChars` (8000) of the container (the email, the chat thread), read on action click. Coordinates from the helper are physical pixels; convert with `screen.screenToDipRect`.

## Routing and slots

The bar is: Glossly menu, Ask (slot 1), Save (slot 2), then slots 3 and 4, then badges. `rankSlots` is the one rule for every action: the top two scores above `router.slotThreshold` (0.5) take slots 3 and 4, the rest above `router.moreThreshold` (0.2) go under More (in the menu); never a third visible slot. Contextual actions are `reply`, `who`, `promises`, `visualize` (`CONTEXTUAL_ACTIONS`); the empty bar's are `reply` (from a reply box, decision 75), `search`, `paste_list`, `paste_summary` (`EMPTY_ACTIONS`). **To add an action:** add its id to one of those lists in `router/types.ts`, give it a 0 to 1 score in `slots.ts`, and the bar, More, keyboard map, and merge all follow. Recall is a badge, not a slot.

`Router.route` returns a `fallback` reason (`local_only`, `no_model`, `timeout`, `error`) when it used rules, `fellBack` when its call moved to the fallback model (and had the 900 ms budget), and `rules` (the rules' decisions and slots) beside a model answer, which `router_done` records with `routeComparison` (decision 61).

## LLM layer

- **Roles**: `fast`, `chat`, `decision`, each `{model, fallback, manual}`; automatic ones follow `updateRoles` on launch and on every catalog change: Decision the fastest structured model, Fast and its fallback off the Decision model, Chat the highest tier (decision 60); Decision with model null ("Use Fast model") only when picked by hand; model refs like `groq:qwen/qwen3.8-27b` or `local:qwen3:8b`. Per-action overrides in `actionModels`. `local` holds the local server's `baseUrl` and the Local only model (`model`, `manual`). Services gives the local provider an empty key once a `baseUrl` is saved; `local:connect`, `local:test`, `local:remove`, and `local:model` manage it.
- **`AiSdkLlm`**: `stream` and `structured`. Falls back to the role's fallback model on 429 or 5xx only before the first token. A 429 is remembered per model until its `retry-after` (`limited`, `retryAfterMs`; a success clears it), and calls skip a limited model while another in the chain is free (decision 60). `ChatRequest.onFallback` tells the caller when a call moves on (the router's budget grows to `router.fallbackTimeoutMs`). Structured calls on reasoning models get `REASONING_ROOM` (512) output tokens on top of their cap. `onFallback` (deps) records `llm_fallback` with action, role, from, to, status, and reason; `onCall` reports every try with its prompt and answer for the opt-in call log (`llm_calls`, decision 61). Structured calls retry once with the validation error appended. JSON mode (no native schema) puts the JSON Schema in the instructions. Reasoning effort per model from `capabilities.json`. Enforces the privacy choice (decisions 12 and 34): under Local only `privacyChain` keeps only local models on a loopback address, and with none a call fails with `local_only` before anything is sent; `hasModel` answers under the same rule, which is how Who, Visualize, and Tasks pick their code paths. A local call with no HTTP answer becomes "Couldn't reach the local model". `ChatRequest.tools` passes tools for one step (Ask's `remember`). It builds every model in a role's chain up front.
- **Token counts** (Step 20.4): `AiSdkLlm`'s `onUsage` reports each call that reached a model (each structured try, each finished stream): action, role, provider, input, output, cached, and reasoning tokens. Services records them as `llm_tokens` metrics, and the metrics summary totals them per action (`features.tokens`).
- **The conversation read** (Step 20.4): one Fast structured call per selection (action `who`, `readWho` in `actions/who.ts`, `prompts/who.md`) returns `messages` (each `{ author, user, starts }`, the first 5 words) and `people`. It sees the selection plus about 1,200 characters before and 300 after (`readInput`, cut at whole lines), with a 400-token output cap. Code accepts it in `people/conversation.ts` (`acceptMessages`): each start found in the selection in order, each author in the text and not a UI label (`isUiLabel`) or else the local parser's speaker there, and `user` from `isMe` when the user's name is set. `Capture.readPeople` caches it per prompt (`whoCache`, `whoPending` dedupe), so Who, Tasks, and (chunk 3) Reply share it; `authorFrom` gives the selected message's author from the read, or the parser's. Reply awaits the read in `Capture.startReply` before answering `reply:start`; `messagesToAnswer` (`actions/reply.ts`) takes the target from the read's messages or the parser's headers, and `replyThread` builds the trimmed, marked thread.
- **Reasoning on streams**: `ChatRequest.reasoning` sets the effort for a streamed call on a model whose capabilities say it reasons (Reply asks for low); other models ignore it.
- **Where the text came from** (decision 54): every call that reads captured text names its source with `describeSource` (app, window title, kind of platform).
- Every new model call goes through `AiSdkLlm`, with an `action` name (used for per-action overrides and metrics) and a prompt file in `core/prompts/`.

## Data

`%APPDATA%\Glossly` (`productName: "Glossly"`): `glossly.db`, `keys\<provider>.bin` (`safeStorage`; the encryption key lives in the profile's `Local State`), `models\` (embedding model), `logs\main.log`.

- **Schema migrations** (`store/migrations.ts`, tracked with `PRAGMA user_version`): 1 every spec table plus `meta`, `settings`, `models`; 2 `commitments.notified_at` and indexes; 3 voice-sample channel/person/draft columns, `style_signals`, `style_notes`, deleting unedited inserts; 4 `people.relationship` and "chat" → "messaging"; 5 `calendar_events` and `calendar_event_people` (decision 37); 6 `commitments.completed_at` (decision 40); 7 `items.entities_pending` (decision 44); 8 deletes every `contractions` style signal and adds `style_notes.channel` (decision 49); 9 `llm_calls`, the opt-in model call log (decision 61; in `LOG_TABLES`: cleared by Delete all data, not exported); 10 `context_docs`, which people, tasks, and events have a vector and the hash of the text it came from (decision 77; in `DERIVED_TABLES`: cleared by Delete all data, not exported), and `context_clock` with its triggers (never cleared). Never edit a shipped migration; add a new one.
- **Settings migrations** (`SETTINGS_MIGRATIONS` in `settings.ts`, applied by `Store.migrateSettings()`, count in meta `settings_migrations`): one-time changes to stored values when a default changes (router 400 → 600 ms, `minWords` 3 → 0, title keys → plain names, `localOnly` → `privacy`). An entry with `from` reads that key, writes its own, and deletes `from` (a rename). Never edit a shipped entry.
- **Vectors**: two `vec0` tables with a cosine metric, both created by `ensureVectorModel(model, dims)`, which recreates them on a model change and reports when every item needs re-embedding. `item_vectors` holds saved items (Recall, Search, Saved). `context_vectors` holds people, tasks, and events, with `kind` as a partition key (`searchContextVectors(v, kind, k)` searches one kind); `context_docs` keeps each row's text hash. Triggers on `people`, `person_aliases`, `interactions`, `commitments`, and `calendar_events` bump `context_clock`; `syncContext` returns at once when the clock equals meta `context_synced_clock`, and otherwise rebuilds every row's text (`contextDocs(store)`, five queries), embeds the rows whose hash changed, drops deleted ones, and stores the clock it read at the start. A task's status isn't in its text, so ticking one off embeds nothing. An older database with item vectors but no `context_vectors` gets the table at launch without re-embedding its items.
- **Item kinds**: `selection` (with an excerpt `ContextWindow`), `note` (from Ask), `chart` (from Visualize; text is the CSV).
- **Export** (`exportAll`): every table except vectors; never keys.

## Privacy rules in code

- Logs (`log.ts`) and metrics (`sanitizePayload`) carry codes, counts, and timings only, never selected text or keys. Site keys are not logged either.
- Password fields are refused by the helper for every read and copy command.
- The keyboard is never hooked (decision 3).
- Nothing leaves this computer under Local only: only a local model on a loopback address, or code (decisions 12 and 34).
