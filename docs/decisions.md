# Decisions

Every choice that differs from the spec (`docs/Highlight-to-Action App Prototype Spec.md`) or that Rayan made after reading it. When code and the spec disagree, this file says which one wins and why.

**Numbers are stable.** Code comments and `STATUS.md` cite them ("decision 15"), so never renumber; add new entries at the end. Each entry: what was decided, why, and where it lives.

By topic: stack 1–8 · capture and overlay 9, 11, 16–18 · data and privacy 10, 12, 19–21, 34, 35 · models and prompts 14, 22–26 · Reply 27–29 · product and design 13, 15, 30, 31, 36, 37, 38, 39, 40, 41.

1. **AI SDK v7, not v6.** v7 is current. API differences that matter: `instructions` replaces `system`; structured output is `generateText({ output: Output.object({ schema }) })` then `result.output`; the full stream is `result.stream` (was `fullStream`), whose `text-delta` parts carry `.text`, plus `error` and `abort` parts; ESM only. Errors: `APICallError` (`statusCode`), `RetryError` (`lastError`), `NoObjectGeneratedError`, `StreamProviderError`. Docs ship in `node_modules/ai/docs/` (migration notes in `08-migration-guides/23-migration-guide-7-0.mdx`). Test mocks are in `docs/testing.md`.
2. **`node:sqlite`, not `better-sqlite3`.** Built into Node 24 and Electron 44, so no native rebuilds. `new DatabaseSync(path, { allowExtension: true })` then `db.loadExtension(require('sqlite-vec').getLoadablePath())`. When packaging, sqlite-vec's DLL must be `asarUnpack`ed.
3. **No `uiohook-napi`.** It installs a global keyboard hook, which the privacy rules forbid. The C# helper runs a mouse-only `WH_MOUSE_LL` hook and learns that a key was pressed (never which) from `GetLastInputInfo`. The "mouse moved 200 px away" check polls `screen.getCursorScreenPoint()` in Electron.
4. **Evals run on Vitest** (`pnpm eval`), not `cargo test`.
5. **Embeddings are local:** `Xenova/all-MiniLM-L6-v2` (384 dims) through transformers.js in an Electron utility process, downloaded on first run into the app data dir, with a notice in setup.
6. **pnpm** is the package manager. Rayan is more used to npm, so keep instructions to him simple.
7. **`DecisionProvider.decide(input, signal)`** takes `{ context, features, collections }` instead of the spec's `(input, questions)`; the questions are fixed by the output contract.
8. **Helper request arguments are top-level fields** next to `cmd` (`{"id":3,"cmd":"context","before":500,"after":500}`).
9. **Tier 2 on the hotkey path uses a focus hand-off.** UIA reads the focused element, but after the hotkey the overlay holds focus. On an action click the shell calls `restore_focus` on the source window, reads `context_container`, then takes focus back (`restore_focus` on the overlay HWND, then `win.focus()`). Blur-to-close is suppressed during the hand-off. Tier 2 is still read only on action click. Copy-fallback selections skip tier 2.
10. **"Delete all data" keeps keys and settings; "Reset settings" is separate.** Delete all data clears `USER_DATA_TABLES` (everything except `settings` and `models`) and vectors, re-seeds the default collections, clears the in-memory Who, Visualize, and Reply caches, and keeps keys, settings, the model catalog, meta, and the embedding model. Reset settings removes saved keys and their test results, clears the catalog, deletes every settings row (so `firstRunComplete` is false and setup runs again, and learned `toolbarWaits` go), and re-registers the default hotkey; saved data stays.
11. **"Try it" in setup captures from the settings window itself**, only while that step is mounted (`setup:try-it {active}`; cleared on unmount, close, or reload). Every other Glossly window stays ignored. "Don't show here" is hidden there (it would set `electron.exe` to hotkey-only).
12. **Local only is strict.** While it is on, nothing goes to a model provider: the router uses rules, Save stores and embeds locally but skips entity extraction, and every model action refuses with "Local only is on" and a way to turn it off. Who is this falls back to its local pass; Visualize charts a parsed table with code. The spec only turns off the router's call. The check lives in one place (`AiSdkLlm.chain()` throws `LlmError('local_only')`), so new actions inherit it. Items saved under Local only are not backfilled with entities later. Step 18 replaced the checkbox with a choice between **All models** and **Local only** and sends Local only calls to a local model when one is configured (decision 34).
13. **Redesign: Windows 11 glass, monochrome.** Acrylic overlay, mica settings window, light or dark with the system, no color accent (black or white primary buttons, grays), Segoe UI Variable, `lucide-react` icons. The bar fits its buttons, with a Glossly menu button at the left so nothing moves when slots fill. DWM rounds the overlay (Windows' fixed 8 px; Electron can't round a transparent window). Windows 10 gets a solid rounded card. The mark is C1, a text cursor plus a sparkle (alternatives in `docs/brand/`). Step 20 may add one accent color and motion; the glass and layout stay. Destructive buttons become filled red there (Rayan, Oct 11).
14. **Who is this uses a model to read people, and code to accept them.** One Fast structured call when the panel opens (never on pill show or every highlight). Code then drops rows under 0.7 confidence, anyone whose name, email, or handle isn't in the captured text, the user (including name variants), and button labels, and merges name fragments. An email attaches to the name next to it; a bare address or shared inbox is never a person. Local only or no key: a strict local pass with no model-written roles. What did I promise reuses the same read (`Capture.readPeople`, cached per text). Reply's author and the person badge still use the local `detectPeople`.
15. **Save has three modes:** Manual (default; the Save button opens the panel), Manual plus a save hotkey (`Ctrl+Alt+S`, saves with no panel and shows a toast with Undo), or Autosave on highlight (the pill's selection is saved as captured; Save becomes Undo). All save to the autoselected collection: the rules' pick first, then the route's collection once it settles.
16. **A shown pill never moves.** The user may already be clicking it. The pill checks for the app's own selection toolbar from 100 ms after mouse-up and places itself once: the full 250 ms wait only where a toolbar is expected (known apps, or learned per app or site in `toolbarWaits`), about 100 ms elsewhere. Only obstacles that appeared after the mouse-down count (baseline diff). Details in `docs/features.md`, Capture.
17. **No word minimum.** Any non-empty, non-password selection shows the pill (`capture.minWords` 0; a stored 3, the old default, was migrated once).
18. **The overlay belongs to its source window.** It stays always-on-top (it never takes focus on the auto path) but closes when another app comes to the front (helper `foreground` event), and Settings opened from the bar closes the bar.
19. **Captured text is saved as written.** Only artifacts are cleaned (`cleanText`: U+FFFC "OBJ", zero-width characters, soft hyphens, non-breaking spaces, line endings, 3+ blank lines). No reflowing or rewording, since joining wrapped lines would break lists, code, and addresses.
20. **People are never created or merged without a confirm.** Fuzzy and first-name matches are offered as "Is this the same X?".
21. **No "open source" button on saved items.** Items keep the app and window title but no URL, so there is nothing to open.
22. **Models pick from enums; code writes the output.** Where options are fixed, the schema says so (`z.enum`): the router's `best_collection` is an enum of the user's collections (a failed call falls back to rules), Who's relationship is an enum, and Visualize's model returns a chart pick (`chart`, `x`, `measures`, `split_by`, `sort`) from which code writes the Vega-Lite spec, so nothing free-form from the model reaches the spec. Confidence fields are not bounded in schemas (a model scoring 85 failed whole calls); code reads 85 as 0.85.
23. **Ask and Reply stream text, not JSON.** Groq doesn't stream strict structured output, and drafts would only appear at the end. Reply's draft headings carry tags (`### Label | kind | tone`) that main checks against `REPLY_KINDS`/`REPLY_TONES`.
24. **Ask saves notes through a `remember` tool on the same stream**, not a second call. The tool result's `say` text streams as the answer.
25. **Default roles with only a Groq key:** Fast = `qwen/qwen3.8-27b` (fallback `openai/gpt-oss-20b`), Chat = `openai/gpt-oss-120b` (fallback Qwen 3.8), Decision = the Fast model. Groq retired its llama chat models (Oct 9). Free-tier limits are per model, so spreading roles across models spreads the limits. Reasoning models get a low reasoning effort from `capabilities.json` (otherwise gpt-oss spends the router's token cap reasoning). Untested models are never auto-picked; a manual pick is never overwritten while it is still available.
26. **Router budget is 600 ms** (`router.decisionTimeoutMs`; 400 timed out on about a third of live calls; stored 400s migrated once). A slow call falls back to rules. While a call is in flight slots 3 and 4 stay empty, and a button once shown is never removed or swapped.
27. **Voice samples are only the user's own writing:** pasted in Profile, replies edited by at least 15% of words, or replies written from scratch ("Write my own"). An unedited draft is the model's text and would pull Reply toward its own style. Migration 3 deleted the old unedited inserts.
28. **Reply's style is measured in code and learned per level.** Picks (weight 1, only on traits where the drafts differ) and edits (weight 2) become signals; a trait becomes a preference when one side holds 70% of the decayed weight of the newest 20 signals, with at least 3 signals for a person, or 5 for a relationship on a kind of platform, or 5 for a kind of platform. Person beats relationship beats platform. All three drafts follow the preferences and still differ by intent (Rayan didn't want a third draft that breaks them). Every 5 edited replies, one Fast call writes up to 5 style notes, each backed by at least 2 draft-and-sent pairs. A switch in Profile turns learning off.
29. **Reply's cache key is the place, the author when found, and the text** (SHA-256 of `siteKey` or process, the selected text with whitespace normalized, and the detected author). Rayan chose this simple key: at worst the same short message in two chats on one site shares drafts, and "None of these" writes new ones. The window title and the surrounding page are left out (unread counts and reloads change them). 20 entries, 30 minutes, memory only.
30. **Scope and order (Rayan, Oct 10; reordered Oct 11):** the remaining features first (local models and the privacy choice, todos and calendar), then polish and the UI upgrade (including the app icon and a new setup), then one combined testing and evals step (live checks, hand tests, eval runners, one eval run), then packaging, then a complete public README. Parked: a subscription, and the spec's optional decision providers (Jev, OpenAI Decisions). macOS work (the Swift helper, macOS onboarding) waits for a Mac; keep everything outside `helpers/windows` OS-neutral.
31. **Reminder toasts have no buttons.** Electron reports toast button clicks only on macOS, so "Mark done" is one click away in Settings > People.
32. **Per-app rules are plain names** (Rayan, Oct 11). "Don't show here" stores the app or site as it reads ("Discord", "Google Docs", "Slack"), not a title key ("Discord |", "- Google Docs") or a process name. A name matches the app's process (`discord.exe`) and the site in a browser, so one rule covers both. Keys ending in `.exe` still match only the process; older title keys still match, and a settings migration renamed stored ones. When the current app is hotkey-only, the menu offers "Show here", which removes the rules that hide it (or stores "auto" over a built-in default). `toolbarWaits` keeps its own internal keys (`siteKeyFor`).
33. **Adding a person is one form everywhere** (Rayan, Oct 11): name, email, handle, about, and relationship, prefilled from what was found, then Create person (`ui/src/people/PersonForm.tsx`). Who is this and Reply's "Add to people" create at once; What did I promise shows the same fields per new person and creates them when the promises are saved.
34. **Privacy is a choice, and Local only can use a local model** (Rayan, Oct 11; Step 18). The `localOnly` checkbox became `privacy`: **All models** (`all`, any configured provider, cloud or local) or **Local only** (`local`); a settings migration (a new `from` field on `SETTINGS_MIGRATIONS` entries renames a key) turned a stored `true` into `local`, and the enum leaves room for the parked subscription. A local server (Ollama, LM Studio, or any OpenAI-compatible endpoint, through `@ai-sdk/openai-compatible` with `json_schema` output, since LM Studio rejects `json_object`) is set up in Keys by address, with no key; its models are provider `local` in the catalog with one generic capabilities entry (structured, streaming, no tools, slow). Under Local only, `privacyChain` keeps only the local models in a role's chain, then `local.model` (the Local only model, filled like a role and kept once picked by hand), and only while the server's address is this computer (`isLoopbackUrl`), so "nothing leaves this computer" holds; a LAN server works only under All models. A local model is never auto-picked as a cloud model's fallback. The router stays on rules under Local only even with a local model (one rarely answers inside the 600 ms budget). **With no local model, Local only falls back to code** (Rayan): the router's rules, Who's text pass, Visualize's code chart, Save without entities, and What did I promise through sentence patterns (`actions/promise-rules.ts`: "I'll…", "can you…", deadlines through `resolveDue`; rows start selected only with a deadline, and the panel says they were found by patterns). Ask, Reply, and the paste summary write new text, so they refuse with "Use all models" and "Set up a local model".
35. **Two Oct 11 answers** (Rayan). The comparison evals (`GLOSSLY_COMPARE`) are skipped in Step 21: if the current setup works and rarely fails, that is enough. Under Local only the router stays on rules even with a local model: 600 ms is already long, so no longer budget for a local Decision model.
36. **What did I promise becomes Tasks; Who is this stays separate** (Rayan, Oct 11). A commitment is a todo with a person, so Step 19's todo action and What did I promise are one action ("Tasks") and one list, which also keeps one fewer action competing for slots 3 and 4. Who is this stays its own action: it answers a different question and costs one small call. What you owe someone doesn't depend only on the message: the Tasks panel shows what the message says (new tasks, or the same, finished, or moved versions of open ones) and, separately, every open task with the people in it. The action id `promises` and the `commitments` table keep their names.
37. **Tasks and events are one action and one tab, stored apart** (Rayan, Oct 11; Step 19.2). A calendar event happens at a set time that people attend (a meeting, lunch, appointment, flight); a task is done by a deadline and checked off. They stay separate records (`commitments` and `calendar_events`, with their own reminders: the due date at 9:00 for a task, `eventReminderMinutes` (15) before a timed event, the reminder hour for an all-day one), but one bar action, **Tasks and events** (id still `promises`), finds both in one Fast call, and one Settings tab, **Agenda**, lists them by day (Overdue, Today, Tomorrow, This week, Later, No date) with All / Tasks / Events and person filters. Reasons: one slot instead of two in a bar that has only two (an invitation would otherwise bring Reply, Tasks, Add to calendar, and Who is this at once), and "what's coming up with Jordan" is one question. A deadline with a time is a task ("send it by Friday 5pm"); an invitation is an event, plus a task when it also asks for something ("bring the deck"). Without a model, `isEventSentence` (a day plus a strong meeting word, or a day and a clock time with a meeting word or no deadline words) decides, and task patterns skip those sentences. **Fallback if one action works poorly** (busy panel, a longer prompt that slows or confuses the Fast model, events missed or doubled as tasks): split it into two actions, Tasks (`promises`) and Add to calendar (a new `event` id in `CONTEXTUAL_ACTIONS`, scored from `eventSentences`), each with its own call and panel; the Agenda tab and the storage stay as they are.
38. **Step 20 is a full design pass, with our own controls** (Rayan, Oct 11). The Agenda tab (decision 37) looked poor: native date and select controls, boxed fields on every row, oversized red delete buttons, uneven margins. Step 20 designs before it builds (mockups first), replaces every native Windows dropdown, date, time, and checkbox control with in-house glossy ones on one spacing and size scale (shadcn or similar only if ours can't look right), and splits the Agenda into a **Tasks** tab and a **Calendar** tab with Month, Week, and Agenda views and a date range, after Google Tasks, Google Calendar, and other modern apps. Tasks and events stay one bar action (decision 37). Lifts "no accent" from decision 13 as already planned.
39. **Step 20.1: our own controls, one scale, monochrome, and the settings tabs regrouped** (Rayan, Oct 11, from the mockups). Every native `<select>`, date, time, checkbox, and radio in both windows is replaced by in-house controls in `packages/ui/src/controls/` over one `Popover` (placed below or above its anchor inside the window, kept attached on scroll and resize, closed by Esc, a click outside, or the anchor scrolling away; keys inside never reach the panel behind). The overlay window is only as tall as its content, so a popover that doesn't fit asks the overlay for room (`RoomContext`) and the window grows toward the side it grows on. Rayan's calls from the mockup rounds: **monochrome** (no accent; the accent part of decision 13 stays closed), 40 px rows and 32 px controls for now, the time list as wide as its field with 32 px rows, hover only darkening text on segmented options, every segmented option as wide as the widest bold label (selecting moves nothing), a square dash for "some selected", subtle hovers that darken checked controls slightly (not grey), small motion like the task-check pop, and one softer red (`#c2463a`) for every filled destructive button in both themes. The sidebar is two groups: Agenda (Tasks and Calendar in 20.2), People, Saved, then under Settings: Profile, Models (Keys merged in: providers first, then roles, then local embeddings and the catalog), Privacy and data (the privacy choice and block list from General, plus Export, Delete all data, Reset settings), General, Metrics. `#keys` and `#data` still open their new tabs, and the window opens on Agenda.
40. **Step 20.2: Tasks and Calendar replace Agenda** (Rayan, Oct 11, from three mockup rounds). **Tasks** (`settings/Tasks.tsx`): quick add, where a date said in the text ("by Friday", "tomorrow", "next week") fills the due chip and leaves the title; filter chips (All, You owe, They owe, Todos) and a person filter; sections Overdue, Today, each later day, No date, and a Completed list that starts closed; rows show "For Jordan Hale" or "Waiting on Maya Chen", and only overdue rows show a date (the section says the rest); checking one off slides it out with an Undo bar; the sidebar shows how many are due today or earlier. **Calendar** (`settings/Calendar.tsx`): Month, Week, and Agenda (a date range), one toolbar shape in every view, tasks on their due day behind a switch, and an editor beside each event (title, day, times or all day with the length, place, people, delete). Week has Google Calendar's gestures: drag on empty time to create, drag an event's bottom edge to resize, drag an event to move it (also to another day), all on 15 minutes; overlapping events share the width. **Events are tempered glass**, Rayan's pick over grey and colored: translucent and frosted with a bright rim and top sheen, tinted faintly from the window's background (sky, periwinkle, lilac, blush, one per event). **Settings:** `weekStart` (Monday by default, Sunday in General) for the calendar and every date picker, and `calendarView`, the last view, which the tab opens on (Week at first). Behind it: migration 6 (`commitments.completed_at`, so Completed can say when), `calendar:add`, `personIds` on `calendar:update`, and reminder clicks opening Tasks or Calendar. Popovers now stack (a picker over the editor), and the segmented highlight is placed in the first paint. The overlay's pickers start weeks on Monday (it gets no settings).
41. **Step 20.3: motion, key hints, the app icon, and setup** (Rayan, Oct 11, from four mockup rounds; `docs/design/mockups/20-3-design-pass.html`). **Motion** uses springs, after research on UI motion (small overshoot that settles, about 2 to 8% and never over 10%; subtle squash before a pop; contents following their container one by one; exits faster, easing in, with no bounce). Three damped springs are sampled into CSS `linear()` curves in `theme.css`: soft (2.8%, for things that appear), pop (7.5%, small things: checks, presses, popovers), gentle (1.3%, big things). Buttons squish to 96% on press and spring back; checks squash, pop past full size, and settle; settings tabs and lists rise in one block at a time; the calendar's new view settles from 97%; events lift 2 px on hover. In the overlay the glass is the window itself, so only what's inside moves (actions pop in, panel parts rise). Windows' "Animation effects" off turns all of it off. **Key hints**: each action keeps its icon on the left with the key in a chip on the right; General's "Show keyboard shortcuts" is Always, On hotkey (the default), or Never; the bar decides once, when it opens, so nothing moves while it's open (Rayan chose this over chips appearing on the first key press, which would widen the bar, over always reserving room, and over chips floating over the buttons). The keys work whenever the bar has focus. **App icon**: Glass (the window's sky-lilac-blush as a glass tile, dark mark, slightly deepened with a faint darker rim for light taskbars) for the window and taskbar; the tray keeps the plain mark; Aurora is the first backup, then Rim (all candidates in `docs/brand/`). **Setup** (built in the next chunk): Welcome with a demo of selecting text through saving a task; Where should AI run (All models or Local only); Add a key with Groq, OpenAI, Anthropic, and Local tabs (Local only shows only the local connection, with what works without one); your name; a models summary; Setting up search (the 23 MB local model, its own step); Try it, whose checklist ticks from the real pill, bar, and action.
42. **How setup was built from the mockup** (Step 20.3, Oct 11; `settings/Setup.tsx`). Choices made while building, within what Rayan approved in decision 41: the privacy choice saves when a card is clicked (it is a setting, and the next step depends on it); Add a key has its own compact key field rather than the Models tab's cards, and only a key that tests is saved (as before); "Emails and chat names" is one optional field split on commas into emails and handles (`splitContacts`), where Profile keeps separate lists; the models step is a read-only summary (picking is in Settings, Models), and under Local only it shows the local model for Fast and Chat and "Rules" for Decision (decision 35), or "Ready without a model"; the search download starts when its step first shows rather than at Finish (Finish still starts it if it never ran). Try it keeps decision 11's capture and adds one push, `setup:tried` (`pill`, `bar`, `action`), sent by `Capture` only for sessions whose foreground window is the Try it window; each tick implies the earlier ones (the hotkey opens a bar with no pill), and nothing unticks. The sample is one chat message, not the old paragraph and message.
