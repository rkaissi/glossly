# Features

What each feature does today, where it lives, and how far it has been checked. "Live" means seen working in the real app on Rayan's machine; "unit" means only unit tests cover it. The live-check backlog in `docs/testing.md` lists everything still waiting for a live pass. Architecture is in `docs/architecture.md`; reasons are in `docs/decisions.md`.

Spec phase mapping: Phase 0 is Capture; Phase 1 is the bar, Ask, Save, and Settings; Phase 2 is People, Who, Tasks and events (formerly What did I promise), and Reply; Phase 3 is Recall, Search, and Visualize; Phase 4 (Windows parts) is Metrics and the evals.

## Capture (the pill, the dot, the hotkey)

**Auto pill.** Drag or double-click any non-empty, non-password selection (decision 17). The pill (200x40 DIP: menu, Ask, Save) shows below the selection end, above if something new is below, or as a dot if both sides are taken. Hover or click expands it into the bar in place.

- **Toolbar wait** (`capture/pill-wait.ts`, decision 16): checks for a new obstacle from `capture.pollStartMs` (100) after mouse-up, every `pollIntervalMs` (35). Full `pillDelayMs` (250) only in `DEFAULT_TOOLBAR_APPS` (Word, PowerPoint, Outlook, OneNote, Notion, Slack, Google Docs and Slides, Word/Outlook/Slack on the web, Medium) or apps learned in `toolbarWaits`; `shortWaitMs` (100) elsewhere. After a short-wait pill, one extra check at 250 ms learns the app or site if its own toolbar (not a menu or tooltip) showed up late. Browser pages without a site suffix are never learned.
- **Obstacles** (`capture/obstacles.ts`): the helper takes a snapshot on every left mouse-down on its own thread (`Baseline.cs`: windows screen-wide plus a column of UIA probes at 20 to 66 px above and below the press). After mouse-up, each found obstacle is `new`, `preexisting`, `tooltip`, or `covers_selection`; only `new` ones move the pill. Windows below the foreground window and click-through windows are skipped.
- **Dot**: an 18 px circle with the mark, in a 40x40 click-through window; the 80 ms cursor poll expands it on hover. `GLOSSLY_FORCE_DOT=1` (dev) forces it.
- **Hiding**: an unfocused pill or bar hides on typing, scroll, a click outside, the cursor 200 px away, or another app coming to the front (decision 18). For 500 ms after the hotkey these signals are ignored (the hotkey itself reads as keyboard activity). A focused bar closes on blur, and a click outside re-checks with the helper 120 ms later whether the bar is really in front (fixes a bar Windows never brought forward). Every close logs `overlay closed {reason, mode, focused, trigger}`.
- **Hotkey** (`Ctrl+Alt+Space`, configurable): opens the bar focused, with copy fallback for apps UIA can't read (clipboard restored). Over a visible pill it expands it. With nothing selected it reads the surroundings (`context_caret`) and opens the empty bar.
- **Per-app modes** (decision 32): block list (password managers, web vaults), hotkey-only defaults (Excel, Google Sheets, terminals, mstsc), and "Don't show here" in the menu, which stores the plain app or site name (`placeNameFor`: "Discord", "Google Docs", "Slack"; unread counts like "(214)" dropped). A name matches the app and the site in a browser. When the app is already hotkey-only the menu item is "Show here", which removes the rule. Settings > General takes the same names (or `name.exe` for the app only).
- **Cleanup**: captured text goes through `cleanText` (decision 19).
- **Debug view** (Settings > General, or the tray): method, trigger, routing stage, fallback reason, timings, pill wait, obstacles, tier-1 context. Rayan normally has it off, so diagnose from `main.log` and events.

Status: live in Notepad, Chrome, and the settings window (pill 116 to 125 ms with no toolbar expected; it never moved in pixel diffs). Not live: other apps in `evals/capture.md`, real selection toolbars, the copy-fallback branch inside the app, plain-name rules and Show here, the stuck-bar fix. Known: Edge's own selection mini-menu counts as a new obstacle. Fixed in Step 20.3, not live (decision 44): the dot sits just past the end of the last selected line (helper `last_line`), and the taskbar flash after the tier-2 hand-off is stopped once focus lands.

## The bar and keyboard map

Glossly menu, Ask, Save to {collection}, slots 3 and 4, badges (person, "N related"). The window grows rightward from a left edge picked at first paint so the widest bar (`MAX_W` 680) fits on screen. Slots 3 and 4 stay empty while a model route is in flight, then fill once; a shown button never goes away. The menu holds More (other actions above 0.2), "Don't show here (site)", Settings, and Close.

Keys (`overlay/keys.ts`): `1` to `4` run the Nth button by position (so the empty bar reads 1 Ask, 2 Search, 3 Paste snippets), `Enter` runs the highlighted one, `Tab` opens the menu with More's first item highlighted, arrows move, `Esc` closes the menu, then the panel, then the bar. In an open panel the digits type into its box (the empty bar opens on Search, focused), so `Alt+1` to `Alt+4` run the buttons from there, and on the bar too (decision 76; unit tests only). Each action shows its key in a chip right of its label when General > Show keyboard shortcuts says so (Always, On hotkey (the default: a bar opened with the hotkey), or Never), decided once when the bar opens (decision 41); the keys work whenever the bar has focus.

In a chat app, someone else's short message gets Reply and Who is this even when the model reads it as a bare question (decision 45). When tier 1 shows no header, the auto path reads tier 2 before slots 3 and 4 show, so the user's own message doesn't get Reply; Tasks takes a slot only with a commitment phrase, a date, or an event in the text (decision 51), and not on "please" alone; Who takes one only when someone other than the user is named (decision 53). Unit tests only. Long collection names show alone in the Save slot ("Client research"); the tooltip says "Save to …" (decision 44). A panel that would run past the bottom (or top) of the window the text came from is capped at the room left in it, if that is at least 320 DIP, and scrolls; the "Nothing selected" strip shows only on the bare bar.

Status: live (Step 13 and 16 checks). Not live: numbering by position, the Step 20.3 fixes (Save label, panels inside the source window, the strip).

## Ask

Streams an answer on the Chat role (`actions/ask.ts`, `prompts/ask.md`). The prompt has the asker's identity (so it doesn't treat the reader as a message's author), the date, time, and time zone, the selection, and surrounding text with a `[SELECTION]` mark. **Saved data** (Step 25.3, decision 77): `retrieveContext` runs on the question and the selection, or the text around the cursor. It finds the saved people, tasks, and events closest to them, each task and event with a label worked out from now ("open, due tomorrow", "today, 1:00 PM to 5:00 PM, in 3 hours", "done Oct 13"), and up to 3 saved notes ("From your note, Oct 10"); "Ask about these" picks the notes instead. A "Used 2 notes · 1 event" chip under the answer (`UsedChip.tsx`) opens to the list, and "Not related" leaves a row out of later answers in that bar session. Privacy > "Use what you've saved in answers" (`context.enabled`, on by default) turns it off; then only notes picked with "Ask about these" go in. With nothing selected it uses the surroundings: "Around their cursor" with a `[CURSOR]` mark, or "What is on their screen". **Memories** (decisions 24 and 78, Step 25.5): asking to remember something calls the `remember` tool (`asked: true`), which saves a memory and says so in the answer. Ask also remembers on its own (`asked: false`) when the question or text shows something worth keeping: a fact about the user or someone they know, a preference, a dated plan. It never saves secrets. Such saves stay out of the answer; the model gets one more step to answer if it saved before writing (`continueAfterTools`). Each save shows under the answer with Undo (`MemoryNote.tsx`), with its text when it was unasked. A memory close in meaning to a saved one (`ask.memoryUpdateSimilarity` 0.8) rewords that one instead, and Undo puts the old wording back. Memories link at once to the saved people they name by full name (`linkNamedPeople`), so they show on the person card. In Settings > Saved they're tagged "Memory" (was "Note") and can be reworded with the pencil (`items:edit`). Local models get no tools, so none of this runs on them. **Ask's other tools** (Step 25.6, decision 78; `actions/ask-tools.ts`):
- **Add a task** and **add an event**: done at once with Undo when asked ("add that to my calendar"), else offered as a row with Add (`AskActionRow.tsx`).
- **Update a saved person**: adds a line to their note or sets their relationship. Only people already saved, matched exactly.
- **About me**: a fact about the user, kept in Profile > "What Glossly knows about you" (`aboutMe`, reword or delete there) and always in Ask's prompt.
- Person edits and facts apply at once with Undo. `Ctrl+C` copies the answer. Errors offer "Add a key", or under Local only with no local model "Use all models and ask" and "Set up a local model".

Answers are tidied for display: no-break and narrow spaces become plain spaces, and "a.m.." loses its extra stop (decision 44).

Status: live (first token about 0.7 s, remember and Undo, Local only). Saved data, memories, Ask's tools, and duplicate checks were live-checked on a throwaway profile (Oct 15, Step 25.8; `docs/testing.md`). Not live: `Ctrl+C`, surroundings with nothing selected, the text tidying.

## Save and save modes

`SaveService` (`actions/save.ts`) inserts at once, then in the background embeds text plus why and extracts entities (Fast role; skipped under Local only with no local model). Undo works for 10 s (`save.undoSeconds`) plus a grace. The panel: collection chips (Tab cycles), a why field, "Saved to Notes · just now", Undo. The label takes the route's `best_collection` once when it settles. Modes (decision 15): Manual, save hotkey (toast with Undo; the default falls back to `Ctrl+Alt+Shift+S` then `Ctrl+Shift+Alt+B` if taken), Autosave (pill shows "Saved", the bar's slot 2 is "Undo save (Ns)"; moves once to the route's collection). Autosave and the save hotkey cost a model call per save (entities, and the router for the hotkey), which can hit Groq free-tier limits; the item is still saved.

Items saved while no model could find their people and places are marked; Privacy offers "Find them" once a model can run (decision 44).

Status: live (all three modes, Undo, embeddings and entities on real data). Not live: the entities backfill.

## Recall and Search

**Recall** (`recall/recall.ts`) runs when the bar opens, on the selection only, locally: items linked to an entity named in the selection (person, company, product, place; names under 3 characters ignored) or a known person's alias, then items similar in meaning at `recall.minSimilarity` (0.78), at most 5, leaving out an item with the same text. A "N related" badge opens cards (snippet with the match marked, why it matched, collection, day, app; Copy, "Not related", "Ask about these").

**Search** is the hotkey with nothing selected: saved items by words then meaning (`recall.searchSimilarity` 0.45), people, and open commitments. Enter inserts the item when the hotkey was pressed in a text field (`canInsert`), else copies; the copy icon always copies.

Status: live (badge, cards, Ask about these, search). Not live: insert from Search.

## Paste (empty bar)

Two actions when nothing is selected (`actions/paste.ts`): **Paste snippets** (`paste_list`, no model) and **Write it for here** (`paste_summary`, one structured Chat call, `prompts/paste-compose.md`). `pasteTarget` reads the kind of spot (email, chat, document, code, other) to set how many snippets (chat 3, document 8, others 5) and the list shape (plain lines in chat, `- ` bullets elsewhere). `pasteSnippets` prefers saved items close in meaning to the text before the caret (`paste.relatedSimilarity` 0.4), else the newest from `paste.recentDays` (7). Write it for here uses only snippets that fit and shapes the text for the spot; it takes slot 4 while the user is writing. The list has List and As saved forms. The panel shows the text in an editable box first; Enter inserts through `insertText`.

Status: the earlier "Paste recent" list was live; the 16.12 rework, As saved, and Write it for here are not.

## People, Profile, and Who is this

- **Identity** (`identity` setting: name, emails, handles): setup's "You" step and the Profile tab. `isMe` matches the full name, the first name alone, first name plus last name or initial, any profile email or handle.
- **People store** (`store/people.ts`): people with aliases (name, email, handle), relationship (friend, family, colleague, professional, acquaintance, stranger, other; null = not set), note, interactions, commitments, voice samples. Rename keeps the old name as an alias; merge and delete need a confirm.
- **Resolution** (`people/resolve.ts`): email or handle alias, exact name or name alias, a first name alone against a saved full name (offered as "Is this the same X?", any app), then Jaro-Winkler above 0.92 among people seen in the same app. Never merged automatically.
- **Who is this** (`actions/who.ts`, `people/who-judge.ts`, `prompts/who.md`, decision 14): a chip per person, the card (aliases, relationship select, note, You owe / They owe, last 5 messages, saved items, Open record), "Is this the same X?", or Create person prefilled with name, email, handle, relationship, and an about line. Emails parse to a real domain ending (`people/emails.ts`), so glued words (`desk@example.comJordan`) are cut off; shared inboxes (no-reply, notifications, newsletters, scheduling) are never people. Router gives Who at least 0.9 for `contact_info` and 0.7 for a name with a phone or personal email. Answers are cached per prompt (20 entries); the local pass is not cached. Since Step 20.4 the same call is the conversation read (who wrote each message in the selection; see `docs/architecture.md`), shared with Tasks and Reply, and the selected message's author is listed first (unit tests only).
- **Person badge**: a known person in the selection with open commitments or a note ("Jordan Hale · 1 open"; several become "Jordan +2 others"). Local, exact matches only.
- **Settings > People**: open commitments across everyone, a searchable list, and the full record at `#people/<id>` (pencil renames, trash morphs to Delete with a short warning only when armed; Manage is merge only, decision 66).

Status: live (setup You step, Profile, Who with the model on the email fixture text, badge, People tab). Not live: the Discord fixture on a real page, real Outlook web, first-name matching, contact cards, shared-inbox and glued-domain fixes, caching, the badge collapse, relationship editing.

## Tasks and events (formerly What did I promise)

One bar action, **Tasks and events**, for promises, requests, personal todos (decision 36), and calendar events (decision 37), and two Settings tabs, **Tasks** and **Calendar** (decision 40; they replaced the Agenda tab). Internally the action id is still `promises`; tasks live in `commitments`, events in `calendar_events`.

- **One call:** one Fast structured call (`actions/promises.ts`, `prompts/extract-commitments.md`) returns `commitments` and `events`, after the conversation read (Who's call, shared and cached; Step 20.4): the read's last author is the message author, and when the selection holds several writers each message goes to the model marked with its author ("[Jordan Hale] …", "[the user] …"), so You owe and They owe follow who said what. Tasks now waits for the read before extracting (one Fast call more of latency when Who hasn't read the selection yet). Before it, the author and the people the message names are matched to saved people (exact matches only), and their open tasks (up to 12) go into the prompt under keys (`t1`…).
- **Code accepts the rows** (decision 63): a new task or event needs a word or its date phrase in the selected text (`inSelection`), so tasks from the lines around the selection are dropped; a row naming the user as the other person becomes the user's task owed to the author. A task with no person goes to the selection's one other person; one other writer's own "I'll …" or "can you …" decides who owes it (`ownerFromText`), and their promises the model missed come from the patterns (`missedPromises`); in a group thread, another writer's ask is the user's task only when it names the user, else it's dropped (`askedBy`, decision 68).
- **Tasks from this message:** each row is `new`, or `same`, `done`, or `moved` with the key of an open task (`open_task` is an enum of the keys sent). Code keeps a row about an open task as that task (owner, person, text), drops a second row about the same task, and turns a `moved` without a readable new date into `same`. `same` rows start unchecked; `done` marks the task done and `moved` sets its new date on save. Due phrases come back as written; `resolveDue` (`people/dates.ts`, 60 phrases tested) turns them into dates.
- **Events from this message** (`calendar/events.ts`, `calendar/when.ts`): title, when and end as written, a length, place, and who attends. `resolveEventTime` reads ranges ("1-2pm", "11-1pm"), end times, and lengths; a day without a time is all day; a timed event without an end lasts an hour. Attendees who resolve exactly to saved people are linked. In the panel: title, day, start and end (no start is all day), place; "Already that day" lists saved events on the same day. An event that looks already saved (the same slot, and a shared distinctive word or, rarely, a very close meaning; `calendar/duplicates.ts`, decision 78) starts unchecked and says "Already saved: …"; Ask's `add_task` and `add_event` offer such a row with Add instead of adding it. A row with no readable day starts unchecked.
- **Already open with these people:** every other open task with the author, anyone named, Who's read, and the rows' people; Done and the date apply at once (`commitments:set-status`, `commitments:update`).
- New task rows: keep or skip, editable task, You owe / They owe, the person, the due date, and for each new person the same fields as Who's Create person (decision 33). Enter saves tasks and events together; the message is stored as an interaction with the people involved.
- **Without a usable model** (Local only without a local model, or no key; decision 34): `rulesEvents` (a day plus a meeting word, or a day and a time without deadline words; title from the meeting word and the author, place after "at" or "in") and the task patterns (`actions/promise-rules.ts`), which skip sentences that read as events, plus `matchOpenTasks`. A note says the rows came from patterns.
- **Settings > Tasks** (`settings/Tasks.tsx`, logic in `tasks-logic.ts`): quick add (a date in the text fills the chip and leaves the title; with the person filter set, the task is owed to that person, decision 65), All / You owe / They owe / Todos with counts, a person filter, then Overdue, Today, each later day, No date, and Completed (closed at first, "Done yesterday"). Rows: round check (slides out, Undo bar), title edited in place, "For …" or "Waiting on …" linking to the person, a date chip on overdue rows only, and on hover a date button and a "…" menu (Open person, Delete: the menu pick arms the shared delete morph in place, decision 66). The sidebar counts tasks due today or earlier.
- **Settings > Calendar** (`settings/Calendar.tsx`, logic in `calendar-logic.ts`, styles in `calendar.css`): Month, Week, and Agenda (a date range); Today and the arrows (in Agenda they move the range by its length); a Tasks switch; New event. Week draws events by time (overlaps side by side) with tasks in the all-day row; drag to create, resize, or move. Month shows chips, "N more" opens that day in Agenda, a click on a day adds an event. Events are tinted glass (decision 40). The editor sits beside the event: title, day, start and end (a new start keeps the length), all day, place, people, delete (trash morphs in place; Save stays visible but disabled while armed or when nothing changed, decision 66). Opens on the last view used; weeks start on the `weekStart` setting.
- Reminders (`reminders.ts`): tasks at `reminderHour` (9) on the due date, or at launch if missed; timed events `eventReminderMinutes` (15) before they start, until they end; all-day events from the reminder hour on their day. Up to 3 per check, events first; clicking opens Settings > Tasks (a task) or Calendar (an event). A moved date or day gets a new reminder.

Status: live (the Step 15.3 extraction, save, card). Not live: everything from Steps 19.1, 19.2, and 20.2 (open tasks, done and moved rows, events, the Tasks and Calendar tabs, todos, event reminders), the shared reader, and new-people details. **The reminder toast never appeared in the dev build** (logged `reminder shown`); likely needs the installer's Start Menu shortcut for the AppUserModelID, or Focus Assist hid it. Check in Step 22 (packaging).

## Reply

Three drafts streamed on the Chat role (`actions/reply.ts`, `prompts/reply.md`), each with a different intent, written as the user to the message's author (or a follow-up when the user wrote it). The prompt has what Glossly knows about the author (note, relationship, commitments both ways, last 5 messages), up to 3 voice samples of at most 300 characters (from this kind of platform only, each marked with where it was written: replies to the same person or relationship, then the samples pasted for this platform, then other replies, then pasted ones marked Any; decisions 57 and 59), learned preferences, and style notes, stable parts first so Groq can cache the prefix (Step 20.4). **Saved data** (Step 25.4, decision 77): the date, time, and zone, then the saved people, tasks, events, and notes closest to the message (`retrieveContext`, as Ask), marked private. The drafts use them when the message touches them ("are you free Thursday?" against that day's events) and share only what suits the reader: a friend in common can be named, a recruiter gets "I have a meeting then". The same "Used N" chip sits under the drafts, kept for cached and resumed drafts, and Privacy > "Use what you've saved in answers" covers it. Reply is not offered for automated mail (no-reply, receipts, shipping, codes, broadcast notices) or the user's own messages (`Features.automated`, `authorIsMe`).

- Panel: Tab cycles drafts, the pencil edits, **Write my own** (an empty fourth box), **None of these** (`N`: Shorter, Longer, More casual, More formal, Different answers, or typed words; writes three new drafts), Copy, Insert. "Add to people" opens the same form as Who (decision 33), prefilled with the author's name, email, and handle, and Colleague in work chat.
- **Insert** gives focus back and pastes. If the focused element is the read-only message, `focus_field` finds the nearest text field not above the selection (never a search or address bar) and pastes there; otherwise the clipboard with "Click the reply box and press Ctrl+V". Nothing is ever sent.
- **Learning** (decisions 27, 28, 49; picks vote only on what every draft must choose (length, tone, kind, capitals, final period, apostrophes); contractions are no longer counted; the every-5 style notes are per kind of platform and may stay as they are; `people/reply-style.ts`, `actions/style-notes.ts`): traits measured in code (length, greeting, sign-off, exclamation marks, emoji, contractions, capitals, final period, apostrophes, dashes, ellipses, line breaks, sentence and word length, punctuation, plus kind and tone from the tags). Kinds of platform (`replyChannel`): email, work chat, messaging, other. Profile > How you write lists samples, preferences, and notes (trash morphs to Delete or Forget; email/handle chips keep the x, decision 66), and a switch for learning (`replyLearning`). Each pasted sample has a platform Select (Email, Messaging app, Work chat, Any), preset by `suggestVoicePlatform` when pasted (decision 59); samples pasted before it were labeled once at startup. Not checked live.
- **Cache** (decision 29): finished drafts per highlight for 30 minutes; closing the panel mid-stream lets the run finish, and reopening resumes it. Edits and the picked draft are not kept.

The drafts answer only the other person's messages: the selection is trimmed to them, the user's headers in the thread are marked "(the user)", and chat headers are read past server tags and badges (Discord), so the recipient is the sender, not a label (decision 47). Only what the other person wrote after the user's last message in the selection is answered; the parser also reads names with spaces and skips badge lines, days and dates, and Discord's hover timestamps (Step 20.4, unit tests only). Since Step 20.4 Reply waits for the conversation read (shared with Who and Tasks, usually cached), so the panel says "Reply to" the read's author from the start, with "Reading the conversation…" (fading in after 250 ms) while an uncached read runs. The target is the other person's messages after the user's last one, quoted once under "The message to answer"; the thread is about 2,000 characters before the selection and 300 after, with the selection's earlier part kept and `[REPLY TO THIS]` where the target sits; after the selection, only the rest of the selected message, never later messages; drafts reply naturally to their messages, picking what matters most, not every point by rule (decision 52). Output cap by channel: 450 tokens for chat, 900 for email and other, with low reasoning on reasoning models (`ChatRequest.reasoning`). Without a read (Local only, a failed call), the header parser gives the author and the target.

**From the reply box** (Step 24, decision 75): the hotkey with nothing selected and the caret in a reply box (a chat composer, an email reply, a comment box) offers Reply in slot 3, ahead of Search, when the text around the caret holds someone's message to answer. The rules (`readField` in `router/field.ts`: an email or chat app, chat headers or a quoted email, a reply-like title) give a first score, and a Decision-role call (`prompts/router-field.md`) settles it while slots 3 and 4 wait; Local only goes by rules. Not offered in documents, search boxes, code editors, for automated mail, or after the user's own last message; a maybe sits under More. Reply then answers the thread before the caret (or a quoted email after it, Outlook-style), and Insert pastes at the caret. In a chat, it answers the last speaker's messages, with the earlier ones as context. A quoted email just below the caret is the message even with page text above the box, cut at the older email it quotes, so its From: line names the sender. Seen live on Oct 14 in the test viewer (chat, email, Outlook-style, and a search box; `docs/testing.md`); on the Outlook-style page the author wasn't found then (the panel said "Reply" without a name), fixed the same day with unit tests and not seen live since.

Status: live in the Step 15 version (three drafts in under 9 s, Insert into a test page's reply box, sample and interaction stored). Not live: `focus_field`, all learning (16.7 to 16.9), Write my own, None of these, the cache.

## Visualize

A bar chart with many or long category names is drawn horizontally whatever the model picked (`crowdedLabels`, Step 21's eval). 1. **Table** (`visualize/table.ts`): Markdown, TSV, CSV, semicolons, pipes, or aligned columns are parsed in code (numbers with separators, currency, %, negatives in parentheses, k/M/B; column types). Otherwise one Fast call returns rows (`prompts/visualize-table.md`).
2. **Chart** (`visualize/visualize.ts`, decision 22): one Fast call returns a chart pick (`prompts/visualize-chart.md`); `specFromChoice` writes the Vega-Lite spec, validated against the Vega-Lite schema with Ajv. No model (Local only without a local model, or no key): `rulesChoice` picks with code. Any failure shows the table with one line why.
3. **Panel** (`VisualizePanel.tsx`): `vega-embed` loaded on open (separate chunk), rendered with `vega-interpreter` because the CSP blocks `new Function`. One series in ink; several use a validated categorical palette. Chart/Table toggle, Copy as image (PNG 2x), Copy CSV, Save (a `chart` item with Undo). Results cached per text.

Status: the earlier version (model-written specs) was live after two fixes; the chart-pick rewrite and the cache are not. Known: a TSV from Notepad may arrive with tabs as spaces and go to the model. Fixed in Step 20.3, not live: category labels stay level or lean 40 degrees, never 90 (`categoryAxis`).

## Settings window and setup

Tabs, in two groups (decisions 39 and 40): Tasks, Calendar, People, Saved, then under Settings: Profile, Models, Privacy, General, Metrics (`settings/`). The window opens on Tasks. Every control is ours (`controls/`): Select, date and time pickers, segmented controls, switches, checkboxes, option cards; destructive buttons are filled red. Setup (`#setup`, Step 20.3, decisions 41 and 42) is one screen per step with progress dots and one primary button: Welcome (the Glass icon and a looping demo: select, pill, bar, Tasks, a saved task), Where should AI run (All models or Local only, saved at once), Add a key (Groq, OpenAI, Anthropic, and Local tabs; Continue needs a working key or local server) or, under Local only, Connect a local model (optional, with what works without one), What's your name (name required; emails and chat names in one optional field), Models are ready (a summary of the roles, or "Ready without a model"), Setting up search (the embedding download starts here; Continue any time), and Try it here (decision 11's capture of the settings window over a sample message; its checklist ticks from main's `setup:tried` pushes: pill shown, bar opened, action run). Steps slide in from the side they come from; choices inside a step change in place.
