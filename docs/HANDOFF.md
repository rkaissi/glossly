## Decisions made (deviations from the spec)

1. **AI SDK v7, not v6.** API notes: `instructions` replaces `system`; structured output is `generateText({ output: Output.object({ schema }) })` then `result.output`; full stream is `result.stream` (was `fullStream`), with `text-delta` parts carrying `.text` plus `error` and `abort` parts; ESM only; errors are `APICallError` (`statusCode`), `RetryError` (`lastError`), `NoObjectGeneratedError`, `StreamProviderError`. Docs ship in `node_modules/ai/docs/` (see `08-migration-guides/23-migration-guide-7-0.mdx`). Test mocks: `MockLanguageModelV4` from `ai/test` (constructor takes `doGenerate` / `doStream` results; result shape in `@ai-sdk/provider` `LanguageModelV4GenerateResult`: `content`, `finishReason: {unified, raw}`, `usage: {inputTokens:{total,...}, outputTokens:{total,...}}`, `warnings`).
2. **`node:sqlite` instead of `better-sqlite3`.** `new DatabaseSync(path, { allowExtension: true })` plus `db.loadExtension(require('sqlite-vec').getLoadablePath())`. Works in Vitest on Node 24 (tested) and inside Electron 44 (verified earlier). No native rebuilds. When packaging, sqlite-vec's DLL must be `asarUnpack`ed.
3. **No `uiohook-napi`.** It also installs a global keyboard hook, which breaks the privacy rule. The C# helper runs a mouse-only `WH_MOUSE_LL` hook and reports keyboard activity through `GetLastInputInfo` (it never sees which keys). The "mouse moved 200 px away" check is done in Electron by polling `screen.getCursorScreenPoint()` while the pill is visible.
4. **Evals use Vitest** (`pnpm eval`), not `cargo test`.
5. **Embeddings:** local `Xenova/all-MiniLM-L6-v2` (384 dims) through transformers.js in an Electron utility process, downloaded on first run into the app data dir, with a notice in first-run setup.
6. **Package manager:** pnpm. Rayan is more used to npm, so keep instructions simple.
7. **`DecisionProvider.decide(input, signal)`** takes `{ context, features, collections }` instead of the spec's `(input, questions)`; the questions are fixed by our output contract.
8. **Helper request arguments are top-level fields** next to `cmd` (e.g. `{"id":3,"cmd":"context","before":500,"after":500}`).
9. **Tier 2 on the hotkey path uses a focus hand-off.** The helper reads from the focused element, and on the hotkey path the overlay holds focus. So when an action is clicked, the shell calls `restore_focus` on the source window, reads `context_container`, then gives focus back to the overlay (helper `restore_focus` on the overlay's HWND, then `win.focus()`). This keeps the rule "tier 2 is read on action click" without reading it early. Blur-to-close is suppressed during the hand-off. Copy-fallback selections skip tier 2.
10. **"Delete all data" keeps keys and settings; "Reset settings" is separate (decided Oct 10, built in Step 12.4).** Delete all data (`data:delete-all`) clears `USER_DATA_TABLES` (every export table except `settings` and `models`) plus vectors, re-seeds the default collections, and keeps keys, settings, the model catalog, meta, and the embedding model. Reset settings (`settings:reset`) removes every saved key and its test result, clears the model catalog (no keys, so nothing in it is usable), deletes every settings row (defaults, `firstRunComplete` false), re-registers the default hotkey, and the Data tab then goes to `#setup`; saved data stays.
11. **"Try it" captures from the settings window itself.** While the setup's Try-it step is mounted, the renderer sets `setup:try-it {active:true}`, and capture accepts the settings window's HWND as a source (`Capture`'s `captureSource` callback; every other Glossly window, the overlay included, stays ignored). The flag clears on unmount, window close, and any full reload. "Don't show here" is hidden for that window (it would otherwise set `electron.exe` to hotkey-only).
12. **Local only is strict (decided Oct 10, built in Step 12.5).** Nothing leaves the machine while it is on: the router uses rules, Save stores and embeds locally but skips entity extraction, and every model action (Ask now; Reply, Who, promises extraction, and Visualize's LLM fallback later) shows "Local only is on" with a way to turn it off. This goes beyond the spec, which only disables the router's call. Once local model support exists (Step 19), those calls go to the local model instead.
13. **Redesign (decided Oct 10, built in Step 13).** Frosted glass using real Windows 11 acrylic, light or dark following the system theme; monochrome, with no color accent; inspired by the ChatGPT and Codex apps. The bar fits its buttons, and a Glossly menu button sits at the left so that nothing ever moves when slots fill. Covers the overlay, the settings window, and setup. Step 22 revisits the "no color accent" part (one accent, motion) after the functional work. The glass and the layout stay.
14. **Who is this uses a model to read people, and code to accept them (decided Oct 10, to build in Step 15.5).** Today it is regex only (`detect.ts`, `features.ts`); the model is not involved. Save's entity call is a different, later call and is not a substitute (it runs only after Save, and it returns a bare name and kind). When a model is available, opening Who sends one Fast-role structured call on the tier-2 text. Code then drops low-confidence rows, drops anyone not actually present in the captured text, drops the user (including name variants), and merges fragments of one name. An `@handle` is kept. An email is attached to a person when it sits next to their name; a bare address is not a person, and no-reply, notification, and scheduling inboxes never are. The address parser stops at the domain, so a word the page glues on (`jordan@example.comCasey`) is not part of the address. Local only, and no key, keep a strict local pass and show no model-written roles. People are still never created automatically. Details and the two acceptance cases are in Step 15.5.
15. **Save has three modes (decided Oct 10, to build in Step 16).** Settings, next to the main hotkey, offers Manual, Manual plus a save hotkey, or Autosave on highlight. All three put the snippet in the autoselected collection (the same choice as Step 15.5.3: rules first, then the route's collection once). Manual is the default and is today's Save button. The hotkey mode keeps that button and adds a shortcut that saves straight away, with no panel. Autosave saves a highlight as it is captured and hides the Save button. Details are in Step 16.

It waits and retries on 429 (free-tier per-minute limit), so a full run takes about 3.5 minutes, and it fails if more than 10% of calls error (errored cases are scored on the rules fallback, which would otherwise hide a broken model call). Rayan asked to keep LLM eval runs rare because of the rate limits.
- The first rules run scored 78.3% type accuracy. These heuristics changed: code keywords count only on lines with code punctuation (plus Python block openers); articles need 35 or more words and 2 or more sentences (was 60 words); name pairs skip chat speaker headers and greeting words, and count 0.3 instead of 0.55 in articles, tables, and code; numeric tokens accept unit suffixes (42ms, 12.1k). Rules-only is now at **98.3% type accuracy and 90% slot match**. The tuning used the same fixtures it is scored on, so expect lower numbers on real selections; Rayan's real examples are the real test.
- Remaining misses: automated mail (shipping notice, all-staff notice, one-time passcode) gets Reply, because the spec scores Reply as `authored_by_other`, which is true for automated mail too. That is a scoring gap for Phase 2 Reply, not a rules bug. Also msg-16 (single first names, so no Who), msg-18 ("please" plus "today" reads as a commitment), and tbl-04 (a prose sentence with 26% numeric tokens, under the spec's 30% threshold).

### Step 5: LLM router eval (run Oct 9)

113 unit tests pass and core `tsc` is clean.

- **Groq retired the llama chat models.** On Oct 9 the key's model list has only these chat models: `qwen/qwen3.8-27b`, `openai/gpt-oss-20b`, `openai/gpt-oss-120b` (plus `allam-2-7b`, which is untested). The first run failed all 60 calls with "model does not exist". The stale llama entries in `capabilities.json` are harmless and still used by unit tests.
- **Reasoning models need a low effort.** `gpt-oss` spends about 500 reasoning tokens by default, which used up the router's 200-token cap and returned empty JSON (`json_validate_failed`). `capabilities.json` entries now take an optional `reasoning` (`none`, `minimal`, `low`); `AiSdkLlm.structured` sends it as `groq.reasoningEffort` (or `openai.reasoningEffort`). Qwen 3.8 uses `none`, gpt-oss uses `low`. gpt-oss is now marked `speed: medium` because reasoning adds latency.
- Single-call latency for the router: Qwen 3.8 (reasoning off, native schema) about 175 ms; gpt-oss-20b at low effort 320 to 550 ms; gpt-oss-120b at low effort 500 to 650 ms. Qwen with `structuredOutputs: false` failed schema validation, so it stays on `json_schema`.
- **Free-tier limits** (from the response headers) are the same for all three models: 1,000 requests per day and 8,000 tokens per minute, **per model**. A router call is about 470 tokens on Qwen, so about 15 router calls per minute per model. Model size doesn't change the limits, but spreading calls across models does: with only a Groq key, `updateRoles` picks Fast = Qwen 3.8 with fallback gpt-oss-20b, and Chat = gpt-oss-120b; a 429 moves to the fallback (a different model with its own limit). There's a unit test pinning these defaults.
- **Result** (`groq:qwen/qwen3.8-27b`, 60 cases, 0 errors): **100% type accuracy, 61.7% slot match**, median 247 ms, 3 calls over 400 ms. Rules-only: 98.3% type accuracy, 90% slot match. Almost every slot miss came from the model scoring `mentions_people` high when the only names were chat speaker headers (it added Who to 17 cases), plus a low `contains_commitment` on 6 commitment cases. `prompts/router-decision.md` now spells out what counts and what doesn't for both fields. **The tuned prompt has not been re-run** (rate limits); run `pnpm eval` once when convenient and record the slot number here.
- The router's 400 ms timeout means a slow call falls back to rules, so the LLM path's slot accuracy matters only when it beats rules. If the re-run stays below the rules' 90%, consider using the model only for `content_type` and `best_collection`, and computing people and commitment scores from rules.

### Step 13.1: acrylic spike (Oct 10, done)

`scripts/spike-acrylic/` (run `node_modules\electron\dist\electron.exe scripts\spike-acrylic`; log in `%TEMP%\glossly-spike-acrylic.log`) opens overlay-like windows (frameless, `focusable:false`, `showInactive`, always on top at `pop-up-menu`, skip taskbar) over a red and blue striped window and reads screen pixels through `desktopCapturer`: blurred acrylic shows as a tinted mix with green raised and little spread, a plain window as the stripes. Electron 44.7, Windows 11 23H2 (22631), 125% scaling. Results:

- **Acrylic works on the overlay, never focused.** `backgroundMaterial: 'acrylic'` blurs and tints what's behind it in light and dark (`nativeTheme`), from the first `showInactive`, through `setBounds` resizes, hide and show, `setIgnoreMouseEvents(true, {forward})`, and losing focus while visible. So the overlay keeps real acrylic; the CSS glass fallback isn't needed (CSS `backdrop-filter` can't blur other windows anyway, it only made a translucent fill).
- **Use a transparent window.** On an opaque frameless window (`transparent: false`) acrylic also works and Electron rounds the corners, but the window gets an invisible frame: `getBounds()` is 2x1 DIP (sometimes 6x4) larger than asked and only `setContentBounds` is exact. With `transparent: true` the bounds are exact and acrylic still fills the whole window rect, but the corners are square (Electron's `roundedCorners` is ignored for transparent windows).
- **Corners through DWM.** `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE = 33, DWMWCP_ROUND)` on the transparent window gives Windows 11 rounding plus DWM's soft shadow and hairline border. The radius is Windows' fixed 8 px; it can't be set to the 12 to 14 px the plan mentioned. Electron has no API for it, so the helper got a `window_corners {handle, corners}` command (`default`, `none`, `round`, `small`; protocol, fixture, and `--check` case). The attribute stays on the HWND through `setFocusable`, hide and show, and material changes.
- **The dot.** Acrylic fills the whole window, so the 40x40 click-through dot window can't be acrylic. `setBackgroundMaterial('none')` alone turns a transparent window opaque white; `'none'` plus `setBackgroundColor('#00000000')` makes it transparent again, and with corners `default` DWM draws no border or shadow. So the dot stays a CSS-drawn circle (translucent fill, hairline, soft shadow) and switches back to acrylic when it expands.
- **Paler after focus.** After the overlay has been really focused (hotkey path, Ask, or Save) and then hidden and made unfocusable, the next `showInactive` draws a paler, more opaque acrylic. Re-applying `'acrylic'` or sending `WM_NCACTIVATE` doesn't fix it; cycling the material (`'none'` plus a clear background color, then `'acrylic'`) does. (`SendMessage` from a PowerShell child also deadlocked the spike while its main thread sat in `execFileSync`; use async calls.)
- **Minimum size:** 30x31 DIP on the opaque variant; the transparent one accepted 40x40 exactly. The pill, bar, and dot are all above it.
- **Mica** on a normal framed window works in light and dark (and shows Windows' solid fallback when inactive, as every Mica window does), so the settings window gets `backgroundMaterial: 'mica'` with a transparent page background.
